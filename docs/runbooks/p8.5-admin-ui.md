# Runbook — P8.5 Admin UI v1

> Console de governança humana para Maia v2. Cinco telas para revisar proposals,
> aprovar via matriz dual, inspecionar drift, explorar traces de runtime e fazer
> rollback de versões. **Este é o único console de governança** — erros aqui
> têm impacto direto sobre a Source of Truth do sistema.

---

## O que é P8.5

P8.5 entregou:

- Next.js 14 App Router em `src/admin-ui/` (Server Components + Client Providers)
- tRPC v11 em `src/admin-ui/trpc/` com tenant context, role guards e mutations auditadas
- NextAuth v5 (pinado em `beta.31`) — `auth()` + `handlers.GET/POST`
- 5 telas de governança: `/inbox`, `/proposals/[id]`, `/audit-log`, `/drift`, `/traces`, `/versions`

> **Redesign 2026-06 (PR #460):** a camada visual foi reconstruída sobre um design
> system próprio (`src/admin-ui/components/ui/`) com shell de navegação agent-first
> (`src/admin-ui/components/layout/`, IA definida em `nav.ts`) e copy em pt-BR.
> Os routers tRPC, contratos e invariantes deste runbook permanecem válidos; o que
> mudou foram caminhos de componentes de página e a experiência de agentes
> (`/agents`, `/agents/new`, `/agents/[agentId]` — `/setup/agents` virou redirect).
- `decideAtomically()` para dual-approval gate atômico (race-safe — toda lógica dentro da tx)
- Modelo de risco de capability com escalation-only (max-only)
- Architecture-lock banner em telas de proposal

**P8.5 não faz:** execução de turnos, avaliação de policies (P9d), trace bodies completos (P10b), OIDC/SAML real (P10).

## Arquitetura geral

```
Browser (React + Tailwind)
    └─ SessionProvider (next-auth/react)          ← providers.tsx (round-2 fix)
        └─ TRPCProvider (tRPC client)
              └─ tRPC v11 routers (protectedProcedure)
                    └─ Drizzle repos via ctx.repos
                          └─ PostgreSQL (compartilhado com runtime)
```

NextAuth v5 fornece `{ handlers, auth }` via `src/admin-ui/lib/auth.ts`. O route handler
é `src/admin-ui/app/api/auth/[...nextauth]/route.ts` que re-exporta `handlers.GET` e
`handlers.POST`.

## Auth — NextAuth v5

### Arquivos relevantes

- `src/admin-ui/lib/auth.ts` — configuração `NextAuthConfig`, exporta `{ handlers, auth }`
- `src/admin-ui/lib/auth-gating.ts` — lógica de gating (dev-auth, timing-safe compare)
- `src/admin-ui/app/api/auth/[...nextauth]/route.ts` — re-exporta `handlers.GET/POST`
- `src/admin-ui/app/providers.tsx` — `SessionProvider` envolve a árvore client

### v5 vs v4 (resumo de migração)

| v4 | v5 (atual) |
|---|---|
| `NextAuthOptions` | `NextAuthConfig` |
| `getServerSession(authOptions)` | `auth()` (sem args) |
| `import NextAuth from 'next-auth'` e `export { NextAuthHandler }` | `export const { handlers, auth } = NextAuth(config)` |
| Route exposta como handler genérico | `route.ts` exporta `handlers.GET` e `handlers.POST` |

Em Server Components, tRPC context e middleware: chame `auth()` (sem args).

### Session shape

```typescript
session.user.id          // ID do usuário (string)
session.user.email       // e-mail verificado
session.user.role        // 'founder' | 'owner' | 'compliance_officer' | 'analyst' | 'viewer'
session.user.tenant_id   // tenant slug do usuário
```

Role e `tenant_id` são derivados do row do DB no JWT callback — **nunca** do valor
fornecido pelo cliente. Impede escalação de privilégio via claims forjados.

### Dev-auth (staging / desenvolvimento)

```env
FEATURE_ADMIN_UI_V1=true
ALLOW_DEV_AUTH=true                        # habilita o CredentialsProvider
ADMIN_UI_DEV_LOGIN_TOKEN=<>=16 chars>     # token compartilhado; timing-safe compare
NEXTAUTH_SECRET=<>=32 chars>
```

Dev-auth **nunca** é ativado em produção (`NODE_ENV === 'production'` bloqueia).
Exige além do token: usuário com `email_verified`, `role` conhecida e `tenant_id`
do credentials batendo com o row do banco.

Produção: providers = [] (fail-closed). Nenhum sign-in até OIDC/SAML ser wired (P10).

### Role guards em tRPC

`protectedProcedure` em `src/admin-ui/trpc/server.ts`:

- `ctx.assertTenant(tenantId)` — rejeita `FORBIDDEN` se `input.tenantId != session.tenantId`
- `ctx.assertRole(...roles)` — rejeita `FORBIDDEN` se o role do usuário não estiver na lista

`tenantId` **sempre** vem do JWT (`ctx.tenantId`). O campo `input.tenantId` é aceito como
sanity-check e deve ser igual à sessão; qualquer discrepância é `FORBIDDEN`.

> **Exceção founder (cross-tenant):** quando `session.user.role === 'founder'`, o resolver
> aceita `input.tenantId` divergente e usa `input.tenantId` como tenant efetivo da operação.
> Esta é uma capacidade cross-tenant explícita — `protectedProcedure` por si só não impede
> o founder de operar em outros tenants. Handlers que admitem founder cross-tenant DEVEM
> auditar a operação em `admin_audit_log` com o tenant efetivo (`input.tenantId`). Endpoints
> que não devem permitir cross-tenant devem verificar explicitamente
> `ctx.assertTenant(input.tenantId)` independentemente do role.

## Telas

### `/inbox` — Proposal Inbox

**Router:** `src/admin-ui/trpc/routers/inbox.ts`

Lista UNION de proposals de todas as fontes (capability, policy_rule, soul_bias, skill,
knowledge). Filtros por tipo, risco, status, ageBucket.

**Fluxo bulk reject:**
- Só proposals com `risk='low'` e sem architecture lock são elegíveis.
- `bulkReject` chama `proposalsUnifiedRepo.bulkReject` que executa cada rejeição via
  `decideAtomically` — cada ID é atômico individualmente. Rows stale não geram audit
  entries e não incrementam `rejected_count`.
- Roles que podem bulk-reject: `owner`, `compliance_officer`, `founder`.

### `/proposals/[id]` — Proposal Detail & Approval

**Router:** `src/admin-ui/trpc/routers/proposals.ts`

#### Architecture-lock banner

Quando `proposal.locks.length > 0`, o componente `ArchitectureLockBanner` é renderizado.
Proposals com lock requerem `role=founder` para aprovar. Em dual-approval com lock, são
necessários **2 founders distintos** (não basta 1 founder + 1 compliance).

#### Fluxo de aprovação (dual-approval gate)

```
approve mutation
  ├─ role guard (founder super-role OU role em requiredRoles)
  ├─ fast-fail: user já aprovou? role já aprovou? (non-authoritative)
  ├─ calcula willSatisfyGate (pre-flight)
  └─ decideAtomically(gateParams)
        ├─ SELECT ... FOR UPDATE na row de proposal (lock)
        ├─ INSERT approval row
        ├─ re-check dup inside tx (authoritative)
        ├─ recompute gate from locked approval list
        └─ source transition se gate satisfeito
```

O `gateParams` passou a incluir `dualRequired`, `requiredRoles`, `allLocks` na
round-2 fix — a lógica de gate é recomputada **dentro** da tx, após adquirir o lock.
Aprovações concorrentes não podem bypasse o gate.

#### Resultado de aprovação

```typescript
{
  status: 'activated' | 'pending_dual_approval',
  dual_complete: boolean,
  source_transitioned: boolean,
  final_status: string,
  remaining_roles: string[],
}
```

### `/audit-log` — Audit Log

**Router:** `src/admin-ui/trpc/routers/audit.ts`

Leitura paginada de `admin_audit_log`. **Somente leitura** — mutations acontecem
inline dentro de outros routers para garantir atomicidade (approve + audit na mesma tx).

**Atenção:** a query bate diretamente na tabela do tenant autenticado. Não há fan-out
para outros tenants sem override explícito no `ctx.tenantId`.

### `/drift` — Drift Incidents

**Router:** `src/admin-ui/trpc/routers/drift.ts`

> **Status atual:** `listDriftAlerts` retorna `{ items: [] }` — o router ainda não está
> conectado ao repositório de `agent_drift_alerts` com escopeamento de tenant. A tela
> `/drift` exibirá lista vazia mesmo que existam alertas na tabela. Wiring pendente em
> PR dedicado.

Lista `agent_drift_alerts` (P4) filtradas por `drift_type`, `severity`, `decision`
(quando implementado).

- **drift_type possíveis:** `papel_drift`, `soul_drift`, `role_drift` (conforme P4/P8b)
- **decision:** `auto_fix`, `queue`, `freeze`, `rollback`
- `listIncidents` depende de P9 (pep_decisions + capability_test_runner) — retorna `[]` até P9 land.
- `listDriftAlerts` também retorna `[]` até o wiring do repositório estar completo.

Para detalhes sobre os tipos de drift e planos de correção, consultar:
- `docs/runbooks/p8d-identity-completion.md` (soul drift)
- `docs/runbooks/p8b-soul-layer.md` (soul biases)

### `/traces` — Trace Explorer

**Router:** `src/admin-ui/trpc/routers/traces.ts`

Lista `runtime_trace_envelopes`. Em P8.5, **nenhum body de trace é retornado** — essa
funcionalidade depende de P10b (runtime_trace + runtime_trace_bodies).

- `listTraces`: retorna `[]` até P10b — tabela `runtime_trace` não está wired.
- `getTrace`: verifica se há `debug_snapshot_grant` ativo para `userId` + `traceId` e expõe
  o resultado em `full_snapshot_available: boolean`. **`redacted_packet` é sempre `null`
  em P8.5** — o router não retorna body independentemente do grant. Grant ativo só sinaliza
  que um body *poderia* ser acessado; a recuperação real requer P10b.
  > **Resposta a incidentes:** `full_snapshot_available: true` confirma que o grant existe,
  > mas o body ainda não é recuperável via API. Para acessar o conteúdo, aguardar P10b ou
  > abrir ticket separado de cutover.
- `requestFullSnapshot`: cria grant TTL-bounded (1–72h) e registra audit automaticamente.
  Este é o único efeito concreto em P8.5 — **criação e verificação de grants**, não entrega de bodies.

Para o schema completo de traces, consultar `docs/runbooks/p10b-runtime-trace.md`.

### `/agents`, `/agents/new`, `/agents/[agentId]` — hub, wizard e detalhe de agente

**Router:** `src/admin-ui/trpc/routers/agents.ts`
**UI:** `src/admin-ui/app/agents/page.tsx` (hub em cards),
`src/admin-ui/app/agents/new/page.tsx` (wizard de 4 passos),
`src/admin-ui/app/agents/[agentId]/page.tsx` (abas Visão geral / Perfil / Versões),
formulário compartilhado em `src/admin-ui/app/agents/_components/profile-form.tsx`.
A rota legada `/setup/agents` redireciona para `/agents`.

O wizard cria um agent + seed `operational_profile_versions` v1 atomicamente
(`createWithSeedAndAudit`). Owner/founder only. A aba **Perfil** propõe novas
versões via `updateProfile` (pré-preenchida pelo procedure read-only
`getProfileVersions`); a aba **Versões** aprova via `approveProfile` (mesma
mutação usada pela tela `/identities`).

#### `priorities` vs `principles` — DUAS coleções distintas (issue #193)

| Campo | Semântica | Auditor | Severidade |
|---|---|---|---|
| `identity.priorities` | Operational labels — o que o agente deve **ponderar** ao decidir foco/ordem de ação | `papelDriftDetector` | Drift soft, sem auto-freeze |
| `identity.principles` | Core value contracts — guardrails comportamentais **invioláveis** | `valoresDetector` | Drift floor `alto` → `frozen` (ou `critico` → `rollback`) |

**Regra de ouro:** nunca duplicar conteúdo entre os dois campos. O resolver
explicitamente NÃO sintetiza `principles` a partir de `priorities` (issue #189),
e o router NÃO auto-copia entre as duas coleções (issue #193).

- **`principles` vazio/omitido** → resolver retorna `core_immutable.principles = []`
  → `valoresDetector` short-circuita com log `valores_drift.no_principles_configured`
  (uma vez por `profile_id`). A VALORES guardrail fica **desabilitada** para esse
  profile, que é comportamento intencional pós-#189/#191. Operadores que quiserem
  ativar o guardrail precisam declarar princípios explicitamente — via wizard
  (campo "principles") ou via updateProfile.
- **`principles` populado** → `valoresDetector` audita as últimas 20 mensagens do
  agente contra esses princípios via LLM-as-judge. Violações disparam alerta com
  severidade hint (`baixo|medio|alto|critico`) que o decision engine floor-eia
  para `alto` no mínimo (qualquer violação de valor congela o profile até
  revisão owner/founder).

#### Anti-pattern proibido

Copiar `priorities` para `principles` (em qualquer lado — cliente, router,
resolver) é o bug class fechado por #189/#191/#193. Promove labels operacionais
a contratos de valor, e o engine congela o profile por desvios que não eram
de valor. Se for adicionar tooling para preencher principles, mantenha-o como
input explícito (não inferência), e idealmente exija review owner antes de
ativar.

### `/versions` — Version History & Rollback

**Router:** `src/admin-ui/trpc/routers/versions.ts`

**AVISO: rollback é irreversível para soul biases.** Uma vez que `fromVersion` avança
para `toVersion`, a versão "atual" é a alvo. Para soul_biases e identity core values,
isso afeta o comportamento imediato do agente.

**SoTs suportados:** `agent_operational_profile_versions`, `policy_rules`, `soul_biases`, `skills`.

**Status atual (admin-ui v1):** todas as SoTs retornam `NOT_IMPLEMENTED` no rollback.
O attempt é sempre **auditado** mesmo em `NOT_IMPLEMENTED` — o operador pode ver que
a tentativa ocorreu e por quem. Use o repo direto ou contate a plataforma.

Desde o redesign 2026-06 a tela expõe o botão **Reverter** (roles
`owner`/`compliance_officer`/`founder`, alvos validados por
`lib/rollback-targets.ts`); enquanto o backend retornar `NOT_IMPLEMENTED`, a UI
mostra um alerta explicando que a tentativa foi registrada na auditoria.

## Invariantes críticas

1. **`decideAtomically()` atômico** (round-2 fix PR #101): toda a lógica de gate (dup-check,
   gate recomputation, source transition, audit) roda dentro de uma única transação DB.
   Aprovações concorrentes não podem bypass o gate.

2. **`capability-risk.ts` — escalation-only**: `deriveCapabilityRisk` usa `Math.max` na
   escala numérica. Um proposal nunca pode auto-declarar risco menor do que o risk floor
   derivado do marker/type. Tool e integration proposals fazem default para `critical`.

3. **`bulkReject` por-ID atômico**: cada ID é processado via `decideAtomically` individualmente.
   Rows em status incompatível (stale) não geram audit entries e não incrementam `rejected_count`.
   O endpoint retorna erro `BAD_REQUEST` se `rejected_count === 0`.

4. **`SessionProvider` wraps client tree** (round-2 fix): `src/admin-ui/app/providers.tsx`
   envolve `SessionProvider` ao redor de `TRPCProvider`. Pages que usam `useSession` DEVEM
   ser `'use client'` components.

5. **Dev-auth dupla guarda**: requer `NODE_ENV !== 'production'` **e** `FEATURE_ADMIN_UI_V1=true`
   **e** `ALLOW_DEV_AUTH=true`. Conhecer um e-mail admin não é suficiente — exige token, email_verified, tenant match.

## Setup local

**Auth em produção: NÃO IMPLEMENTADO — fail-closed até OIDC/SAML (P10).**
`auth.ts` retorna `providers=[]` em produção. A página de sign-in chama
`signIn('magic-link')`, que só está registrado em dev/staging com as flags abaixo.
`GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` não existem no código — não preencha.

```bash
# 1. Dependências (legacy-peer-deps enquanto Issue #128 não for resolvido)
cd src/admin-ui && npm install --legacy-peer-deps

# 2. Variáveis de ambiente
cp .env.example .env
# Obrigatório: NEXTAUTH_SECRET (>=32 chars), DATABASE_URL
# Dev-auth (staging/desenvolvimento APENAS):
#   FEATURE_ADMIN_UI_V1=true
#   ALLOW_DEV_AUTH=true
#   ADMIN_UI_DEV_LOGIN_TOKEN=<token com >=16 chars>
# Produção: NÃO configure ALLOW_DEV_AUTH. Sem OIDC/SAML, sign-in retorna
# "no providers configured" (fail-closed intencional até P10).

# 3. Servidor de desenvolvimento (da raiz do repo)
npm run dev:admin

# 4. Smoke test (dev/staging com dev-auth ativo)
# Log in via magic-link: POST /api/auth/callback/magic-link com
#   { email, token: ADMIN_UI_DEV_LOGIN_TOKEN, tenantId }
# Abrir /inbox → submeter proposal de risco=low → verificar aprovação automática
```
